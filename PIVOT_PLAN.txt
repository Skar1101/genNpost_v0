HARD RULES (carried forward from the pre-pivot build -- do not relitigate these without a real reason)

  - NEVER automate the X account. No code path may post, reply, comment, like, or retweet on/from X,
    automatically or otherwise -- draft-only, permanently. This is a hard stop, not a current
    limitation to eventually lift.
  - LinkedIn (Parrot) is the ONE confirmed, explicit, written exception to that rule -- real automated
    posting on Telegram Approve. Scoped to LinkedIn only; X and Substack are unaffected.
  - Substack (Heron) stays draft-only by deliberate choice, not a technical gap: no official Substack
    publish API exists, and every "post to Substack" tool that exists is an unofficial,
    session-cookie-authenticated workaround against Substack's own Terms of Use. No Substack
    credentials of any kind are stored anywhere in this codebase, and none should be.


CONTEXT

The new product goal: a multi-agentic platform for busy professionals, founders, and hustlers with little time for content creation, that:
  1. Researches trending topics per the user's domain
  2. Learns the user's context/taste over time
  3. Generates text+picture content for multiple platforms and schedules it on a calendar
  4. Is controlled via Telegram
  5. Auto-posts on allowed platforms

Codebase investigation found the vision is much closer to already-built than a fresh product would be:

  1. Research trending topics per domain
     STATE: Real. Raven agent (agents/raven.js) does ranked research, writes state/data/research-latest.json.

  2. Learn user taste/context
     STATE: Real. state/memory.js persists profile.json, voice-examples.json, approved-drafts.json,
     rejected-drafts.json (with reasons), performance-log.json. memory.loadContext() feeds Koel's prompt
     (prompts/koelWrite.js:77). Telegram approve/reject actions write back into this memory
     (server/routes/telegram.js:427,470). This is a genuine feedback loop, not a stub.

  3. Multi-platform text+picture, scheduled on calendar
     STATE: Mostly real. Koel has per-platform prompt packs for LinkedIn/X/Substack (sub-agents/koel/).
     Calendar (web/src/components/SlotGrid.jsx + state/scheduleStore.js + state/assetsStore.js) is a
     genuine drag-drop hourly grid, not a mockup. Image generation (tools/generateImage.js) is wired into
     the calendar-generate flow but is an opt-in checkbox, not default-on.

  4. Control via Telegram
     STATE: Real but asymmetric. Draft-queue approve/reject and one-tap "send now" both work.
     GAP: calendar/slot-scheduled posts are NOT gated by a Telegram approval at fire time --
     scheduler/slotDelivery.js auto-fires LinkedIn posts unattended when a slot's time arrives, with no
     final human check.

  5. Auto-post on allowed platforms
     STATE: Real for LinkedIn only. Real OAuth + REST publish (utils/linkedinClient.js). X and Substack
     push a ready-to-copy draft to Telegram instead of posting via API (X now charges $0.015-$0.20/post
     at the API level, which is why this wasn't automated).

So the actual work is NOT "build the vision from scratch" -- it's (a) closing a real safety gap,
(b) two scoping decisions already made with the user, and (c) turning a working single-user tool into a
usable multi-user product with minimal new infrastructure.

Decisions made with the user:
  - X stays manual copy-paste for v0 (no new per-post API cost, no new integration). Market this honestly
    as "LinkedIn auto-posts, X is one-tap-ready" rather than "auto-post everywhere."
  - Instagram is deferred to v1 -- Meta Graph API + business account + app review is an external,
    unpredictable blocker not worth risking the launch date on.
  - [2026-09-12] V0 will NOT support multiple users/tenants. This retroactively takes Steps 2, 3, and
    5.5 out of scope (see their markers below) and makes Step 5's enforcement piece moot for now --
    the app stays single-account, and effort goes into polish/UX (landing page + IA overhaul, see below)
    instead of multi-tenancy plumbing nobody needs yet.


MARKET FIT

Confirmed via research: there is real, active demand for exactly this combination ("clear whitespace
opportunity for AI agents targeting time-constrained founders," 81% of marketing-tech leaders piloting AI
agents, tailored per-platform AI content outperforming generic AI content by 2.4x engagement). Existing
competitors each cover only one slice:

  - Schedulers (Buffer, Postiz): distribute content you already wrote -- no research, no taste-learning.
  - Ghostwriters (Taplio, Supergrow, Typefully, TweetHunter): single-platform (LinkedIn or X), no deep
    trending-topic research feeding them, most rely on browser-session automation (ToS/ban risk) rather
    than official APIs.
  - Repurposers (Blotato, Repurpose.io): format one input into many platforms -- no ideation/research
    step, commoditized category.
  - Brand-voice platforms (Jasper): enterprise-oriented, not chat-first, not built for a solo founder's
    Telegram workflow.
  - ClimbX -- the closest direct competitor found: research your niche -> voice-matched drafts ->
    engagement suggestions -> learns from edits/performance -> schedule. X-only, web-dashboard-first
    (not chat-first), $29-39/mo. genNpost's multi-platform + Telegram-first angle is real
    differentiation against it, not just against the broader category.
  - Mira, Postiz, Hermes Agent -- reviewed for structural/UX inspiration (see LANDING PAGE + IA
    OVERHAUL below), not direct feature-for-feature competitors.

No player found combines: trending-topic research -> persisted taste-memory -> multi-platform draft
generation with images -> visual calendar -> chat-based control -> real auto-post, in one product. That
full stack is what's already built here -- it's a genuine differentiator, not a hypothesis to validate
from zero.

Risk flags to carry into launch:
  - Silently auto-firing a real professional's LinkedIn post with no last-second human check is a trust
    risk for this exact ICP (people protecting real reputations) -- must be fixed before onboarding
    anyone but the current single user. [FIXED -- see Step 0]
  - "Understand user taste" is a real, valuable subsystem already -- worth foregrounding in marketing,
    not just a footnote feature.

  Flip the "Generate an image too" checkbox in FillSlotModal/calendar-generate flow

  a per-image cost estimate in the UI before generation (reuses existing tools/generateImage.js provider

⏭️ Step 2 -- Telegram-chat-ID-as-identity (skip building a login system)
  SKIPPED BY DECISION (2026-09-12: not building multi-user support in V0, see HARD RULES/CONTEXT above).
  Extend state/accounts.js (which already has an account-slug concept, currently hardcoded to one
  default) so a new Telegram chat ID auto-provisions its own account slug and isolated state folder on
  first contact. This removes the need for a separate auth/login system for v0 entirely.

⏭️ Step 3 -- Per-tenant data isolation
  SKIPPED BY DECISION (same 2026-09-12 call).
  Migrate the JSON stores under each account's folder (scheduleStore, assetsStore, memory, costStore,
  etc.) to one SQLite file per tenant -- a natural extension of the existing per-account-folder layout,
  not a Postgres rewrite. Gets real transactional safety for concurrent multi-user writes without new
  infra to manage.

✅ Step 4 -- Per-user LinkedIn OAuth (code-level done; not yet load-bearing, V0 stays single-user)
  Generalize the existing single-account LinkedIn OAuth flow (utils/linkedinAuth.js,
  /api/parrot/oauth/start /callback) to store one token per account slug instead of one global token.
  Required before a second real user can connect their own LinkedIn.

🟡 Step 5 -- Per-user cost guardrails
  Cost entries can now carry an account tag and state/costStore.totalForAccount() exists to query
  per-account spend (utils/costTracker.js, state/costStore.js). NOT done: threading `account` through
  the ~20 existing cost-recording call sites across agent files, and no actual budget cap is enforced
  anywhere yet -- tracking exists, enforcement doesn't. Moot for now per the single-user V0 decision.
  Extend config/guardrails.js + state/costStore.js (both already real and working globally) to cap LLM
  calls and image generations per account per period. Needed because this product's cost stack (research
  + taste-aware writing + images) is heavier per user than a plain scheduler.

✅ Step 5.5 -- Consolidate to a single Telegram bot identity (2026-09-12)
  DONE. Titto's bot (TELEGRAM_BOT_TOKEN) is now the one Telegram bot for the user by default -- Heron
  and Parrot both merge into it unless you deliberately opt into a dedicated bot for either. Heron
  already had "same-bot mode"; the real gap was Parrot, which had no same-bot path at all and always
  required its own PARROT_TELEGRAM_BOT_TOKEN (server/routes/parrotTelegram.js). Fixed in
  server/routes/telegram.js: added a Parrot same-bot sender with its own explicit "Approve & Post to
  LinkedIn" keyboard (never confusable with a plain draft-queue Approve), and taught the shared 'd|a'
  callback handler to detect a LinkedIn draft (memory.getDraft(...).platform === 'linkedin') and run
  the real parrot.postApprovedDraft() publish flow instead of the generic "queue" transition -- on
  ANY chat, not just a dedicated Parrot one. server/index.js now falls back to telegram.js's Parrot
  sender the same way it already did for Heron's.
  Default behavior: leave HERON_TELEGRAM_BOT_TOKEN/HERON_TELEGRAM_CHAT_ID and
  PARROT_TELEGRAM_BOT_TOKEN/PARROT_TELEGRAM_CHAT_ID all empty -> everything (Titto chat, Heron drafts,
  Parrot/LinkedIn approvals) flows through ONE bot token and ONE chat. Setting a dedicated
  *_CHAT_ID still lets you route Heron/Parrot content to a separate chat/channel on the SAME bot
  (opt-in, not required); setting a dedicated *_BOT_TOKEN still spins up a fully separate bot
  identity for that agent, for anyone who wants it kept apart. This is routing-only -- Parrot's and
  Heron's agent logic (topic assignment, Koel calls, LinkedIn publish) is untouched.
  NOTE: the user's own .env currently still has HERON_TELEGRAM_BOT_TOKEN and PARROT_TELEGRAM_BOT_TOKEN
  set to real dedicated-bot tokens (all three chat IDs happen to already be the same number). Those
  explicit tokens take precedence over the new same-bot default, so the merge won't visibly take
  effect until those two lines are cleared/removed from .env.


SUB-AGENT SCOPE FOR V0

  - Koel -- keep, required. The actual per-platform writer (LinkedIn/X/Substack prompt packs);
    everything else calls into it.
  - Parrot -- keep, required. Owns the only real auto-publish integration (LinkedIn OAuth +
    utils/linkedinClient.js) -- this is feature #5 (auto-post).
  - Quill -- keep the logic, trim the volume. Its daily X topic-assignment -> Koel-drafts pipeline is
    what makes X's "manual copy-paste" flow (see X decision above) feel like real automation to the user
    -- drafts are just waiting in Telegram. Cut the default ~24 drafts/day down for v0 to reduce noise
    and LLM cost; tune volume up later based on real usage.
  - Heron -- defer, optional. Substack/long-form topic curation + draft-only hand-off. Not in the 4
    stated v0 features, and since it never auto-posts it carries no safety risk sitting dormant. Revive
    only if beta users specifically ask for newsletter/thought-leadership content.
  - Analyst -- out of scope for v0 unless already load-bearing elsewhere; not mentioned in the 4 stated
    features.

TELEGRAM: PHOTO-GROUNDED GENERATION + CHANGE-TIME FROM CHAT ✅ (2026-09-12)

Reported: sending Titto a photo with an instruction caption ("write a x post for morning motivation
based on this picture") just saved the photo+caption straight to the library instead of generating
anything; and there was no way to change a scheduled post's time from Telegram at all.

1. Photo + instruction now generates instead of just saving.
   Root cause: server/routes/telegram.js's `bot.on('message')` treated EVERY photo as "finished
   content, file it as-is" -- it never reached Titto's intent parser, and even if it had, nothing in
   the codebase could actually look at an image (no vision-model call existed anywhere).
   Fix: added utils/vision.js (describeImage() -- one gpt-4o-mini vision call via the existing
   utils/llm.js pipeline, so it's cost-tracked and guarded like every other LLM call). telegram.js now
   downloads the photo once and, when there's a caption, runs it through titto.handleMessage() WITH
   the image attached; agents/titto.js's write_post and write_linkedin_post branches describe the
   photo and fold that description into extraInstructions before calling Koel/Parrot, so the resulting
   draft is actually grounded in what's in the picture. handleMessage() returns `imageUsed: true` when
   this happened; telegram.js only falls back to the old save-to-library behavior when it's false
   (plain captions, questions, chit-chat -- unchanged from before).
   Found and fixed a real bug while testing this: the intent classifier read "based on this picture"
   as a request to GENERATE an image (wrong branch) because it had no idea a photo was attached --
   fixed by appending an explicit "(a photo is attached...)" hint to the text sent to the classifier
   whenever an image is present.
   Verified live with real API calls (not mocked): fed a real photo to utils/vision.describeImage()
   directly (got back an accurate, specific description), then ran the full
   titto.handleMessage({ text: '...based on this picture', image }) path end-to-end -- confirmed
   intent=write_post, imageUsed=true, and Koel produced 3 real drafts that genuinely referenced the
   photo's actual content, delivered via the same telegramSendDraft callback Telegram uses. Test
   drafts + test conversation session removed from real app state afterward.

2. Change a scheduled post's time from Telegram.
   Added a "🕐 Change time" button to the asset-delivery card (telegramCore.js's assetKeyboard(),
   alongside the existing Posted/Snooze buttons -- this is the card Telegram already sends when a
   scheduled slot fires). Tapping it asks for a new time; the next plain message is parsed with
   chrono-node (added as a new dependency) so "tomorrow 9am", "friday 6pm", "in 2 hours", or an
   explicit "2026-09-20 14:00" all work, not just a bare HH:mm -- then calls the same
   assetsStore.setSchedule() the Studio date picker uses (see the Studio fix above), so it's the exact
   same reschedule path, just reachable from chat instead of only the dashboard.
   Verified chrono-node's parsing directly against the app's real IST-based scheduling assumptions
   (confirmed the dev machine's system timezone actually is IST, so no offset math needed) --
   "tomorrow 9am", "friday 6pm", and an explicit date all resolved to the correct UTC instant.

Both features require restarting the running server (`npm start`) to take effect -- code changes to an
already-running Node process don't apply until it restarts, same as the earlier Telegram bot-token merge.
